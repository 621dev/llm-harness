# ADR 0012: 도메인을 견적 계산 하나로 줄인다 (ADR 0005는 유지)

- 상태: 확정
- 날짜: 2026-08-03
- 관련: **ADR 0005(공유 엔진 + 독립 도메인 폴더 — 이 결정으로 전제가 약해졌으나
  폐기하지 않는다)**, ADR 0010(패턴 측정 — "실사용 run 0건"을 여기서 발견했다)

## 배경

`domains/`에 폴더 5개가 있었다. ADR 0005가 "공유 엔진 + 독립 도메인 폴더"를 정하고
1호(`cloud-ops`)로 검증한 뒤, 2~5호가 `scripts/new_domain.py`로 쉽게 만들어졌다.

**넷은 한 번도 쓰이지 않았고, 하나는 쓰인 뒤 멈췄다.**

| 도메인 | 실제 run |
|---|---|
| `server-engineering-learning` | **6건** (2026-07-25~27, 체인 3스텝 완주) — 그 뒤 사용 없음 |
| `cloud-ops` · `ncp-snapshot-drill` · `centos-eol-migration` · `cloud-ops-consulting` | **0건** |

README가 2~4호에 대해 이미 "**실제 LLM run 미실행**"이라고 적어두고 있었다. 만들어 두고
안 쓴 상태가 2~3주 이어졌고, 그동안 **패턴 측정을 8회 돌렸다**.

> **⚠️ 정정(같은 날)**: 이 ADR의 초판은 "5개 전부 실제 run 0건"이라고 적었다. **틀렸다** —
> `server-engineering-learning`의 run 6건을 놓쳤다. 원인은 집계 명령이
> `.claude/worktrees/`를 제외한 것이고, **도메인 작업은 애초에 워크트리에서 한다**
> (run 산출물은 `_workspace/`라 워크트리 간 공유되지 않는다).
> 저장소가 이미 그 run을 기록하고 있었는데(`planner.py:53` "실제 5개 task를 e2e로
> 돌려보니", 체크리스트) **집계를 문서보다 더 믿은 것**이 실수다.
> `count_fitness_rejections.py`를 워크트리까지 세도록 고쳤다.
>
> **삭제 결정은 유지된다** — 그 6건은 07-25~27에 몰려 있고 그 뒤 쓰이지 않았다. 다만
> "아무도 쓰지 않았다"가 아니라 **"쓰였다가 멈췄다"**가 정확한 서술이다.

## 결정

**`cloud-ops`(견적 계산)만 남기고 나머지 4개를 삭제한다.** 사용자 결정(2026-08-03).

| 도메인 | 추적 파일 | 처리 |
|---|---|---|
| `cloud-ops` | 25 | **유지** — `run_estimate.py` + Fetcher 실측 가격 + xlsx 템플릿 5종 |
| `server-engineering-learning` | 8 | 삭제 |
| `ncp-snapshot-drill` | 3 | 삭제 |
| `centos-eol-migration` | 3 | 삭제 |
| `cloud-ops-consulting` | 3 | 삭제 |

합계 17개 파일 / 879줄. `cloud-ops`가 유일하게 커스텀 스크립트를 가진 도메인이고 실제
업무(견적)에 대응한다.

### 삭제 전에 한 것 — git으로 복구 못 하는 것을 먼저 건졌다

`_workspace/`는 gitignore 대상이라 **폴더를 지우면 영구 소실된다.** 전수 확인해서 2건을
찾았다:

- `centos-eol-migration/_workspace/server-hostnames.md` (443바이트)
- `ncp-snapshot-drill/_workspace/backup-recovery-procedure.md` (2,977바이트)

둘 다 작업 규칙의 "실제 운영 서버 정보(호스트명/IP)는 `_workspace/`로 이동" 정책의
결과물이다 — **일부러 git에서 뺀 실제 운영 데이터**다.
`harness-mvp/_workspace/archive/domains-cleanup-20260803/`으로 옮긴 뒤 삭제했다.

**이 과정에서 `.gitignore` 구멍을 하나 찾았다.** 처음 보관 위치를 저장소 루트
`_workspace/`로 잡았는데 `git status`가 바로 잡았다 — 규칙이 `harness-mvp/_workspace/`와
`domains/*/_workspace/`만 덮고 있어서 **루트는 추적 대상**이었다. 그대로 커밋하면 실제
호스트명이 저장소에 들어갔다. `**/_workspace/`를 추가해 위치와 무관하게 막았다.

### 워크트리·브랜치는 정리하지 않았다

워크트리 4개 중 3개가 삭제된 도메인용이고, 브랜치 4개 모두 `domains/` 기준 3점 diff가
**0**이다(삭제 전 실측 — v21 §5가 "보존 브랜치"로 적어둔 근거가 이미 소멸했다).

그래도 손대지 않는다: **워크트리 브랜치 배정은 앱이 소유하는 영역**이고, 손으로 만들면
앱이 다른 이름을 배정해 중복이 생긴 전례가 있다. 도메인 폴더가 없어진 지금 그 워크트리는
자연히 쓸 일이 없으므로 앱에서 정리하면 된다.

## ADR 0005를 폐기하지 않는 이유

"여러 도메인" 전제는 약해졌지만 **구조 자체는 여전히 값을 한다**:

- `cloud-ops`는 **독립 `config.json`**(역할별 모델·상한)으로 엔진과 분리돼 있다. 도메인이
  하나여도 엔진 설정과 업무 설정을 섞지 않는 건 유효하다
- `_workspace/` 분리가 **운영 데이터를 git 밖에 두는 경로**다. 위 사고가 그 필요성을
  다시 보여줬다
- 새 도메인이 필요해지면 `scripts/new_domain.py`가 그대로 동작한다 — 되돌리는 비용이 낮다

**다만 정직하게 남길 것**: ADR 0005의 검증은 "도메인 5개를 만들 수 있다"였고, **"만들 수
있다"와 "쓰인다"는 다르다.** 4개가 그 차이의 증거다. 다음에 도메인을 추가할 때는
**실제로 돌릴 task가 있는지 먼저 확인할 것** — `new_domain.py`가 무료라서 만들기 쉬운 게
오히려 함정이었다.

## 남는 것

**실사용 run이 여전히 0건이다.** 도메인을 줄인 게 이 문제를 푼 건 아니다 — v21 §11의
2순위가 "실사용 도메인 run"이고, 그게 라우팅 근거·rubric 난이도 기준·패턴 유용성을
동시에 푸는 유일한 길이다. 이제 대상이 `cloud-ops` 하나로 명확해졌다.

기각한 대안: **`domains/` 구조 자체를 없애고 `harness-mvp/` 안으로 흡수.** 도메인이 하나면
분리 자체가 과할 수 있지만, 그러면 운영 데이터와 엔진 코드가 같은 트리에 섞이고 `.gitignore`
경계가 흐려진다. 위에서 겪은 사고가 바로 그 경계의 문제였다.
