# 현재 구조 유지 vs ECC 전환 — 상세 비교와 판단 (2026-07-29)

`affaan-m/ECC` 재분석(`harness-ecc-reanalysis-2026-07-ko.md`)에서 층위 차이와 적용
항목을 정리했다. 이 문서는 그 다음 질문에 답한다: **엔진을 계속 쓸 것인가, ECC식
설정층으로 전환할 것인가.**

결론부터: **전환하지 말고, 대신 "엔진 전체"가 아니라 "패턴별"로 유지 여부를 따로
판단하라.** 근거와 결정 기준은 아래에.

## 0. 질문이 이항 선택으로 잘못 놓여 있다

"현재 구조 vs ECC"는 두 가지를 혼동한다.

- **ECC는 우리 엔진의 대안이 아니다.** ECC는 Claude Code 설정층(마크다운 프롬프트
  모음)이고, 우리 엔진은 여러 LLM을 호출·기록·게이팅하는 Python 코드다. ECC로
  갈아탄다고 "더 나은 오케스트레이션"이 생기는 게 아니라 **오케스트레이션이
  없어진다**.
- **우리 엔진은 한 덩어리가 아니다.** 팀 패턴 4종 + 공용 인프라의 합이고, 각각의
  근거가 다르다. "엔진을 버린다"는 결정은 근거가 다른 6개 결정을 한꺼번에 하는 것이다.

그래서 이 문서는 **구성요소별로** 판단한다.

## 1. 층위 비교 (요약)

| | ECC | 우리 |
|---|---|---|
| 정체 | Claude Code 설정층 (agents 67 / skills 281 / commands 94, 전부 프롬프트) | 실행·평가 엔진 (Python 4,513줄 + provider 913줄) |
| 실행 주체 | Claude Code가 실행, ECC는 규칙 주입 | 엔진이 provider를 호출 |
| 제어 흐름 | 모델이 루프를 돈다 | 하네스가 돈다(패턴 3종), `agentic_task`만 모델 |
| 여러 모델 | 같은 규칙을 여러 하네스에 **이식**(Cursor/Codex/Gemini 어댑터) | 여러 벤더를 **한 태스크에 붙여 비교** |
| 재현 단위 | IDE 세션 | `run-<id>/` 디렉터리 |
| 안전 | 스킬 문서의 consent **지침** | 코드 강제(`risk_level=high` + `approval.json` 없으면 미실행) |
| 검증 | — | 테스트 386개 (6,647줄) |
| 학습 | Memory Vault, continuous-learning | `learning.py`(2026-07-29 도입) |

**핵심 차이는 강제력이다.** ECC는 "승인 없이 하지 마세요"라고 쓰고 모델이 따르기를
기대한다. 우리는 승인 파일이 없으면 실행 경로가 막힌다. ADR 0007에서 경계가 실제로
뚫린 경험(문서를 믿었더니 에이전트가 워크스페이스 밖을 읽었다) 이후 이 차이의 값을
알게 됐다.

## 2. 실측 근거 — 여기가 판단의 중심이다

### 무엇이 측정됐나

| 조건 | 1차 (07-28) | 2차 (07-29) |
|---|---|---|
| `direct_call` | 3/3, 28.3초, $0.0093, 1회 | 2/3, 33.8초, $0.0126, 1회 |
| `hierarchical_delegation` | 2/3, 37.3초, $0.0094, 2회 | 2/3, 56.8초, $0.0185, 4회 |

**두 번 측정해서 두 번 다 체인이 우위를 보이지 못했다.** 1차는 체인 구성 결함
(ADR 0008 이전 — 리뷰 코멘트를 최종물로 냈다)이 원인이었고, 그걸 고친 2차에서는
동률이 됐다. 비용은 1.5배, 지연 1.7배, 호출 4배다.

### 그런데 이 데이터로 결론을 낼 수 없는 이유가 둘 있다

**(1) n=3이다.** 1건 차이는 통계적으로 무의미하다.

**(2) 판정자가 신뢰할 수 없다.** 2차 불합격 2건이 **둘 다 판정자 문제**였다 —
rubric에 없는 요건("시각 자료")을 발명해 불합격시키면서 같은 응답에서 "매우 훌륭하게
작성되었습니다"라고 칭찬했고, 요청이 시킨 검토 섹션을 "심사자 역할 침범"으로 오판했다.
프롬프트를 개편했지만(2026-07-29) **효과는 아직 미검증**이다.

### 그리고 결정적으로 — 측정된 적 없는 패턴이 둘이다

| 패턴 | 기계 장치 | 비교 측정 |
|---|---|---|
| `direct_call` | 적합성 게이트 | ✅ 2회 (가장 값이 확인된 부분) |
| `hierarchical_delegation` | 역할 체인 + 누적 히스토리 + ADR 0008 합성 | ✅ 2회 (우위 미입증) |
| **`fan_out_judge`** | **judge + synthesizer + blind 익명화 + 구독 후보 상한** | ❌ **0회** |
| `iterative_refinement` | 라운드 루프 + `check_pass` | ❌ 0회 |
| `agentic_task` | 경계 강제 + 턴 기록 | e2e 1회(파일 생성 확인), 비교 측정은 해당 없음 |

**가장 많은 기계 장치를 가진 `fan_out_judge`가 한 번도 비교 측정되지 않았다.**
측정 스크립트(`measure_pattern_value.py`)는 `direct` vs `chain`만 돌린다. 즉
"다모델 비교에 값이 있나"라는 원래 질문은 **아직 시도조차 안 된 상태**다.

이건 전환 판단에 결정적이다 — 전환하면 이 질문의 답을 **영구히 못 얻는다**.

## 3. judge 의존도 — 취약점의 위치

| judge에 의존하는 것 | 영향 |
|---|---|
| `fan_out_judge` (`judge.evaluate`) | 후보 비교·합성 전체 |
| `iterative_refinement` (`judge.check_pass`) | 합격 판정·피드백 |
| **측정 자체** (`check_pass`) | 모든 패턴 비교의 신뢰도 |

**패턴 4종 중 2종 + 측정 인프라가 같은 부품에 매달려 있다.** 그 부품을 두 라운드에
걸쳐 고쳤는데 아직 신뢰도가 입증되지 않았다. 이게 현재 구조의 최대 리스크이고,
ECC 전환과 무관하게 해결해야 하는 문제다(ECC에는 judge 대응물이 아예 없다).

## 4. ECC 전환의 실제 비용

**(1) 마이그레이션 경로가 없다.** 공유 코드가 0줄이다. 전환 = Python 5,426줄 +
테스트 6,647줄 폐기 후 프롬프트 라이브러리 신규 작성.

**(2) 잃는 것이 구체적이다.**

- 파일 기반 재현성 — `run-<id>/`에 plan/candidates/judging/final/metrics/errors가
  남아 다시 해석할 수 있다. ECC의 재현 단위는 IDE 세션이다.
- 코드 강제 게이트 — `risk_level=high` 강제, Safety 스캔, 예산 상한 3층, 도구 경계
  CLI 인자. ECC는 전부 지침이다.
- 다벤더 비교 능력 — ECC에 대응 개념이 없다.
- `domains/cloud-ops`의 Python 자동화(Fetcher + xlsx). **실제 운영 중**이고 ECC가
  호스팅할 수 없다.

**(3) 장기 목표와 방향이 반대다.** 목표는 "자율 에이전트를 **감싸는** 하네스"다.
`agentic_task`가 그 지점이고(경계·기록·승인을 하네스가 책임진다), ECC는 에이전트
안에서 에이전트를 잘 쓰는 것 — 감싸는 게 아니라 타는 쪽이다.

**(4) 이미 이점만 흡수했다.** ECC가 우리보다 나았던 건 두 가지였다 — 에이전트 튜닝,
run 간 학습. 2026-07-29에 둘 다 엔진 위에 올렸다. 남은 차이는 ECC의 **폭**(281 스킬)
인데, 그건 우리 절제 원칙(ADR 0003/0005)과 정면으로 상충하고 대가가 있다 — ECC에는
"스킬을 관리하는 스킬"이 25개 있다.

## 5. 판단

### 전환하지 않는다

위 4가지 비용 중 (1)(2)(3)만으로도 전환은 순손실이다. (4)까지 보면 전환의 유일한
명분이던 "ECC의 이점"이 이미 우리 쪽에 있다.

### 대신 — 패턴별로 유지 여부를 따로 판단하라

"엔진 유지 vs 폐기"가 아니라 **어느 패턴이 값을 증명했나**로 쪼갠다.

| 구성요소 | 판단 | 근거 |
|---|---|---|
| 공용 인프라(`run_store`/`safety`/`budget`/`learning`/`planner`/`router`) | **유지** | 남는 패턴이 하나라도 있으면 필요하다. 패턴과 독립 |
| `direct_call` + 적합성 게이트 | **유지** | 2회 측정에서 가장 효율적(1회 호출, 최저 비용). 값이 가장 확실한 부분 |
| `agentic_task` | **유지** | ECC에 대응물 없음. 장기 목표의 실현 지점. 경계 검증 자동화까지 있음 |
| `hierarchical_delegation` | **보류 — 3차 측정이 근거** | 2회 우위 미입증. 판정 신뢰도 문제로 아직 사형선고는 못 함 |
| `fan_out_judge` | **측정 필요 — 판단 유보** | 기계 장치가 가장 많은데 비교 측정 0회. 지금 버리는 것도 지키는 것도 근거가 없다 |
| `iterative_refinement` | **트리거 대기 유지** | opt-in 전용이라 비용을 안 쓴다. 실제 필요가 관측될 때 측정 |

**절제 원칙(ADR 0003/0005)을 우리 자신에게 적용하는 것**이 이 판단의 요지다.
"필요할 때만 만든다"는 "값을 증명하지 못한 것은 접는다"의 대우다.

## 6. 결정 기준 (다음 측정에서 무엇을 보고 무엇을 정하나)

### 3차 측정 (한도 회복 직후, judge 프롬프트 개편 후 첫 측정)

먼저 **판정 신뢰도**를 본다 — 이게 통과 못 하면 나머지 숫자는 읽을 가치가 없다.

- 결과 JSON의 `unmet_rubric_items`가 불합격마다 **rubric 항목을 명시**하는가
- feedback에 `[rubric 항목 미지정 불합격]` 표시가 **안 붙는가**

→ 표시가 계속 붙으면: **judge 신뢰도 문제로 확정.** `fan_out_judge`와
`iterative_refinement` 둘 다 신뢰할 수 없다는 뜻이고, 패턴 판단보다 judge 재설계가
선행 과제가 된다(규칙 기반 grader 비중을 늘리는 방향 — ADR 0004 재검토).

판정이 신뢰할 만해진 뒤 체인을 본다.

- **체인 합격률 > direct** → 유지 확정. 비용 1.5배를 정당화할 유형을 찾는 단계로
- **체인 ≈ direct** (3차도 동률) → **키워드 자동 라우팅에서 제외하고 opt-in으로 강등.**
  같은 값에 1.5배를 기본값으로 두는 건 적합성 게이트 철학과 모순이다
- **체인 < direct** → 폐기 검토. ADR로 기록하고 `router` 라우팅 제거

### 5차 측정 — `fan_out_judge`를 처음 조건에 넣는다 (2026-07-29 개정)

`fan_out` 조건은 `measure_pattern_value.py`에 **추가됐다**(후보 N + judge 1 + 판정 1).

**아래 원래 기준은 그대로 쓸 수 없다 — 원리적으로 발동하지 않는다.**

> - **fan_out > direct** → 다모델 비교의 값이 처음 입증된다. 엔진의 존재 근거가 확정
> - **fan_out ≈/< direct** → judge + synthesizer + blind 익명화 전체가 근거를 잃는다.
>   **이때가 진짜 축소 결정 시점이다** — 그때 남는 건 `direct_call` + `agentic_task` +
>   인프라이고, 그건 "ECC 전환"이 아니라 **"우리 엔진의 절제된 버전"**이다

문제는 **4차에서 direct가 이미 3/3(만점)**이라는 것이다. 합격률로는 `fan_out > direct`가
불가능하고 `≈`만 나올 수 있다. 즉 이 기준을 그대로 적용하면 **rubric의 천장 효과가
엔진 핵심을 지우는 결정을 자동으로 촉발한다.** 3차는 바닥 효과, 4차는 천장 효과였으니
합격률 한 축으로는 다섯 번째도 같은 운명이다.

**개정: 축을 둘로 하고, 축소 결정은 두 축이 모두 가리킬 때만 한다.**

| 축 | 무엇을 보나 |
|---|---|
| 합격률 | 여전히 본다. 단 **양쪽 만점은 "동등"이 아니라 "구분 실패"로 읽는다** |
| **정면 비교**(신규) | direct와 fan_out 산출물을 **blind로 직접 비교**해 승패를 센다. 천장이 없다 |

정면 비교는 엔진 자신의 `judge.evaluate`를 쓴다(blind 레이블 + 무작위 순서로
position/identity bias를 이미 다룬다). 측정용 판정자를 새로 만들면 "측정에 쓴 판정자와
엔진이 쓰는 판정자가 다르다"는 문제가 생긴다.

- **fan_out이 정면 비교에서 우세** → 값이 처음 입증된다. 합격률이 동률이어도 마찬가지다
  (동률은 rubric의 해상도 부족이므로)
- **정면 비교도 대등하거나 열세 + 합격률도 동률** → 그때가 축소 결정 시점이다.
  비용 근거가 함께 필요하다(fan_out은 호출이 direct의 3~4배다)
- **정면 비교가 매번 근소한 차로 갈린다** → 판정 해상도 문제로 본다. 그때 필요한 건
  결론이 아니라 **더 어려운 프롬프트**다(현재 1종, n=3)

**남는 미측정 변수를 반드시 함께 말할 것**: 이 측정의 fan_out 후보는 **전부 같은
백엔드**다(다른 조건들과 같은 통제 원칙). 그래서 검증되는 건 "후보 N개 + judge + 합성"이고
**운영 config가 실제로 쓰는 모델 다양성(claude+codex)은 검증되지 않는다.**

## 7. 그래도 ECC식 전환이 맞는 경우

아래 중 하나라도 참이면 재검토할 값이 있다.

1. **4차 측정에서 `fan_out_judge`도 값을 못 낸다** + 3차에서 체인도 못 낸다 →
   다모델 오케스트레이션 전체가 근거를 잃는다. 다만 그때도 답은 "ECC로 전환"이 아니라
   "`direct_call` + `agentic_task`만 남기고 인프라는 유지"다.
2. **산출물이 코드로 바뀐다** — ECC의 강점 91개(언어별 패턴/TDD/verification)가
   비로소 유효해진다. 현재 산출물은 문서·절차서라 해당 없다.
3. **여러 사람이 각자 IDE에서 작업하는 팀이 된다** — ECC의 하네스 간 이식성과 Memory
   Vault의 인수인계 목적이 맞아떨어진다. 현재는 단일 엔진 배치 실행이다.
4. **유지 비용이 실제로 문제가 된다** — 지금은 테스트 386개가 회귀를 잡아주고 있어
   비용이 관리되는 쪽이지만, 손대는 사람이 줄면 판단이 달라진다.

## 결론

**전환하지 않는다. 근거는 "우리 구조가 우월하다"가 아니라 "전환은 순손실이고, ECC의
이점은 이미 흡수했다"다.**

**대신 지금 필요한 건 전환 여부 판단이 아니라 두 가지 측정이다** — 3차(judge 신뢰도 +
체인)와 4차(`fan_out_judge` 최초 측정). 그 결과에 따라 **패턴을 줄이는** 결정을 하면
