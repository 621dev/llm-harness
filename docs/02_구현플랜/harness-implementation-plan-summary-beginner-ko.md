# 구현 플랜 요약 (쉽게 풀어쓴 버전)

이 문서는 우리가 만들려는 "여러 AI를 활용하는 시스템"의 설계 계획을, IT를 잘
몰라도 이해할 수 있도록 풀어쓴 것이다. 정확한 기술 사양은
`harness-implementation-plan-ko.md`에 있고, 이 문서는 "우리가 왜 이렇게 만들기로
했는지"를 비유를 곁들여 설명한다.

## 1. 우리가 만드는 것을 한 문장으로

작업의 성격에 따라 "여러 AI에게 동시에 시켜서 비교하는 방식"과 "AI들에게
역할을 나눠 순서대로 시키는 방식" 중 알맞은 걸 자동으로 골라서 실행하고, 그
과정을 전부 기록해두는 시스템이다.

이걸 회사에 비유하면: 어떤 안건은 "여러 팀에게 각자 안을 받아서 제일 좋은 걸
고르는 회의"로 처리하고, 어떤 안건은 "리서치팀 → 기획팀 → 검토팀 순서로 넘기는
결재 라인"으로 처리하는데, 어떤 안건에 어떤 방식을 쓸지 자동으로 정해주고, 회의록과
결재 서류를 전부 파일로 남겨두는 시스템을 만드는 것과 같다.

## 2. 왜 방식을 두 가지로 나눴는가

### 방식 1: 여러 명에게 동시에 시키고 비교하기 (`fan_out_judge`)

설계안 검토나 글쓰기처럼 "여러 관점을 비교해봐야 좋은 답이 나오는 일"에 쓴다.
예를 들어 세 명의 전문가에게 각자 따로 기획안을 받아보고, 그중 가장 좋은 안을
고르거나 여러 안의 장점을 섞어서 최종안을 만드는 것이다. 이 방식에서는 심사위원
역할(아래에서 설명할 "Judge")이 필요하고, 여러 안을 비교한 결과를 남긴다.

### 방식 2: 역할을 나눠서 순서대로 시키기 (`hierarchical_delegation`)

자료 조사나 단계별 검토처럼 "역할 분담이 중요한 일"에 쓴다. 예를 들어 먼저
리서치를 잘하는 담당자에게 자료 조사를 맡기고, 그 결과를 설계 검토를 잘하는
담당자에게 넘겨서 다음 단계를 진행하는 것이다. 이 방식에서는 비교할 여러 안이
애초에 없으므로 심사위원(Judge)이 필요 없다.

### 왜 하나로 합치지 않았는가

두 방식을 하나로 억지로 합쳐서 "모든 일에 항상 리서치 → 비교 → 심사를 다
거치게" 만들 수도 있었다. 하지만 그러면 간단한 일에도 매번 여러 단계를 거치게
되어 시간과 비용이 낭비된다. 마치 점심 메뉴 하나 정하는데도 이사회를 소집하는
것과 같다. 그래서 "이 일에는 어떤 방식이 맞는지"를 먼저 판단하고, 필요한 방식만
골라서 쓰도록 설계했다.

## 3. 시스템을 이루는 담당자들

우리 시스템은 회사 조직처럼 몇 개의 역할로 나뉜다.

- **Planner (기획 담당)**: 들어온 요청을 보고 "이건 어떤 종류의 일인지, 위 두
  방식 중 뭘 써야 하는지, 성공 기준이 뭔지"를 미리 정리하는 역할.
- **Model Runner / Subagent Runner (실무 담당)**: 방식 1에서는 여러 AI에게
  동시에 일을 시키는 담당자, 방식 2에서는 역할별 AI에게 순서대로 일을 넘기는
  담당자.
- **Judge (심사위원)**: 방식 1에서만 등장. 여러 안을 놓고 어떤 안이 좋고 나쁜지,
  왜 그런지 점수와 이유를 남긴다.
- **Synthesizer (편집장)**: 심사위원의 의견을 참고해서 여러 안의 장점을 모아
  최종본을 완성하는 역할.
- **Safety Evaluator (검수팀)**: 최종본에 위험하거나 부적절한 내용, 개인정보
  노출 같은 문제가 없는지 마지막으로 점검하는 역할.
- **Run Store (문서보관함)**: 위 모든 과정에서 나온 요청서, 기획서, 각 안,
  심사 결과, 최종본, 비용/시간 기록, 실패 기록을 전부 파일로 보관하는 곳.

## 4. 왜 모든 걸 파일로 남기는가

회의를 하고도 회의록을 안 남기면, 나중에 "왜 그때 그런 결정을 내렸지?"를 아무도
설명할 수 없다. 우리 시스템도 마찬가지다. 나중에 "어떤 AI가 어떤 일을 잘했는지",
"왜 이 안이 최종 선택됐는지", "비용이 얼마나 들었는지", "어디서 실패했는지"를
확인하려면 모든 중간 과정을 파일로 남겨둬야 한다. 이렇게 기록이 쌓이면 나중에
"이 방식이 정말 효과가 있었는지"를 데이터로 확인하고 개선할 수 있다.

## 5. 실패했을 때는 어떻게 하는가

일을 시켰는데 AI가 답을 못 주거나 이상한 답을 주는 경우가 있다. 이럴 때 매번
사람이 판단하게 두면 시스템이 불안정해지므로, 미리 규칙을 정해뒀다.

- 한 번 실패하면 한 번 더 시도해본다.
- 그래도 실패하면 "이번 건은 실패"라고 기록하고, 나머지 안들로 계속 진행할 수
  있으면 진행한다 (방식 1의 경우).
- 순서대로 진행하는 방식(방식 2)에서 중간에 실패하면, 거기까지 성공한 부분을
  "일부만 완성된 결과"로 남기고 사람에게 확인을 요청한다.
- 검수팀(Safety)에서 문제가 발견되면 결과를 내놓지 않고 사람에게 확인을
  요청한다.

## 6. 구독으로 쓰는 AI도 이 시스템에 쓸 수 있는가

쓸 수 있다. AI를 쓰는 방법은 "쓴 만큼 돈 내는 방식"(API)과 "매달 정액 요금 내는
구독 방식"이 있는데, 우리 시스템은 둘 다 지원하도록 설계했다. 다만 구독
방식은 일정 시간마다 쓸 수 있는 양이 정해져 있어서(핸드폰 요금제의 데이터
한도와 비슷), 방식 1(여러 명에게 동시에 시키기)처럼 한 번에 여러 번 부르는
방식보다는 방식 2(순서대로 하나씩 시키기)에 더 잘 맞는다.

## 7. 어떤 순서로 만들어 가는가

건물을 지을 때 기초 공사부터 하듯, 우리도 순서를 정해뒀다.

1. **기초 골격 만들기**: 어떤 방식을 쓸지 나누는 기본 틀과, 기록을 저장하는
   창고(Run Store)부터 만든다. (지금까지 완료된 부분)
2. **가짜 AI로 먼저 연습하기**: 진짜 AI를 연결하기 전에, 미리 정해진 답을 내는
   "가짜 AI"로 방식 1(여러 명에게 동시에 시키기)이 제대로 도는지 확인한다.
3. **가짜 AI로 방식 2도 연습하기**: 마찬가지로 방식 2(순서대로 넘기기)도 가짜
   AI로 먼저 확인한다.
4. **기획 담당(Planner) 만들기**: 들어온 요청을 보고 방식 1과 2 중 뭘 쓸지
   정하는 규칙을 만든다.
5. **자동 안내 시스템(선택 사항)**: 명백한 요청은 기획 담당을 거치지 않고
   바로 방식을 정해서 시간을 아낀다.
6. **심사위원과 편집장 만들기**: 방식 1 전용 기능을 완성한다.
7. **검수팀 만들기**: 최종본을 안전한지 점검하는 기능을 만든다.
8. **전체 조율 완성**: 지금까지 만든 모든 담당자를 하나로 연결하고, 실제로
   명령을 내릴 수 있는 진입점을 만든다.
9. **전체 테스트**: 두 방식 모두 처음부터 끝까지 제대로 도는지, 실패 상황도
   잘 대응하는지 확인한다.

이 순서를 지키는 이유는, 진짜 AI를 바로 연결하면 비용도 들고 결과가 매번
달라져서 시스템 자체에 문제가 있는지 AI 답변이 이상한 건지 구분하기 어렵기
때문이다. 그래서 가짜 AI로 "틀은 제대로 도는지"부터 확인하고, 그다음에 진짜
AI를 연결한다.

## 8. 앞으로의 확장 계획

지금 만드는 건 가장 기본적인 뼈대이고, 이후에 순서대로 더 붙여나갈 기능들이
있다.

1. **반복 실행 가능하게 하기**: 같은 요청을 다시 넣었을 때 똑같은 구조로 결과가
   나오는지 확인 (지금 단계)
2. **성적표 시스템 만들기**: "100번 중 몇 번 성공했는지" 같은 지표를 자동으로
   측정하는 기능 추가
3. **AI 선택 규칙 다듬기**: 실제 AI 서비스(OpenAI, Anthropic, Google 등)와
   연결하고, 일의 난이도에 맞는 AI를 자동으로 고르게 함
4. **안전 점검 강화**: 검수팀 기능을 실제로 위험한 결과를 걸러내는 관문으로
   승격
5. **시스템 스스로 개선하기**: 반복되는 실패를 분석해서 매뉴얼을 고치고, 고친
   전후 성과를 비교
6. **한눈에 보는 화면 만들기**: 어떤 AI가 얼마나 잘했는지, 비용은 얼마나
   들었는지 보여주는 화면 추가

## 9. 나중에 추가한 안전장치 4가지

이 계획을 세운 뒤, `jikime/harness-lab`이라는 교육용 레포를 살펴보고 도움이 될
만한 아이디어 네 가지를 우리 계획에 반영했다.

1. **간단한 일은 굳이 여러 명 안 부르기 (적합성 게이트)**: 아주 간단한 질문에도
   매번 여러 AI를 불러서 비교하면 시간과 돈이 낭비된다. 그래서 본격적으로
   기획 담당(Planner)에게 넘기기 전에, "이 일이 정말 여러 명을 부를 만큼
   중요한가"를 먼저 저렴하게 확인하는 문지기를 하나 더 뒀다. 간단한 일이면
   AI 한 명에게만 물어보고 끝낸다.
2. **위험한 일은 사람 확인부터 받기 (사람 승인 체크포인트)**: 중요하거나
   위험도가 높다고 판단된 일은, 기획서(Plan)가 나온 즉시 바로 실행하지 않고
   사람에게 먼저 "이대로 진행해도 될까요?"라고 확인받은 다음에야 실행한다.
   결재 서류에 팀장 사인을 받고 나서야 다음 부서로 넘기는 것과 같다.
3. **왜 이렇게 정했는지 메모 남기기 (ADR)**: 구조를 바꾸는 중요한 결정을 내릴
   때마다 "왜 이렇게 정했는지"를 짧은 메모로 남겨둔다. 나중에 새로 합류하는
   사람이 "왜 이렇게 만들었지?"라고 의아해하지 않도록 하는 회의록 같은 것이다.
4. **주기적으로 안 쓰는 부분 정리하기**: 시스템을 계속 고쳐나가다 보면 더 이상
   안 쓰는 규칙이나 낡은 메모가 쌓인다. 이걸 그대로 두지 않고, 일정 주기마다
   "이거 아직도 필요한가?"를 점검해서 필요 없는 건 지운다. 서랍 정리와 같다.

## 10. 지금까지 진행 상황

7절의 1~9번 단계(기초 골격부터 전체 조율 완성까지) 전부 끝났다. 가짜 AI로 두
방식(여러 명에게 동시에 시키기, 순서대로 넘기기) 모두 처음부터 끝까지 돌려봤고,
9절에서 설명한 안전장치 4가지(적합성 게이트, 사람 승인 체크포인트, ADR, 정기적
정리 습관)도 실제로 코드에 반영해서 확인했다. 명령어 하나로 실제 실행해볼 수 있는
진입점(`python -m harness.cli run/replay/approve/reject`)도 만들었고, 49가지
테스트로 "제대로 도는지" 확인도 마쳤다.

앞으로 남은 건 8절의 2번 단계(성적표 시스템)부터다. 자세한 최신 상황은
`../03_진행상황/harness-progress-checklist-ko.md`에 항상 최신으로 정리해둔다.

## 11. 용어 정리

| 용어 | 쉬운 설명 |
| --- | --- |
| Planner | 요청을 분석해서 계획을 세우는 기획 담당 |
| Model Runner / Subagent Runner | 실제로 AI를 불러서 일을 시키는 실무 담당 |
| Judge | 여러 안을 비교 평가하는 심사위원 |
| Synthesizer | 여러 안의 장점을 모아 최종본을 만드는 편집장 |
| Safety Evaluator | 최종본의 위험 요소를 점검하는 검수팀 |
| Run Store | 모든 기록을 보관하는 문서보관함 |
| 복구 전략 | 실패했을 때 어떻게 대응할지 미리 정해둔 규칙 |
| API vs 구독 | 쓴 만큼 내는 방식 vs 매달 정액으로 내는 방식 |
| 가짜 AI(mock) | 진짜 AI 대신 미리 정해진 답을 내는 연습용 대역 |
| 적합성 게이트 | 간단한 일까지 여러 AI를 부르지 않도록 미리 걸러주는 문지기 |
| 승인 체크포인트 | 위험도 높은 일은 실행 전에 사람 확인을 받게 하는 절차 |
| ADR | "왜 이렇게 정했는지"를 남겨두는 결정 메모 |
